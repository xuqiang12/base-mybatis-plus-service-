## 后续文件怎么放

下一次发布时新增 `1.0.1/`，将该版本的相关 SQL 放在一起。新文件使用简短英文名，例如 `V2__user_status.sql`；文件第一行注释写清具体改动。这是命名示例，当前没有新增业务或 V2 脚本。

目录版本表示发布批次；文件的 `V1__`、`V2__` 表示 Flyway 执行顺序，两者独立。Flyway 使用两个下划线分隔版本号和说明，同一服务、同一迁移历史内不能重复版本号。

已执行的脚本不改文件名和内容，后续变更新增脚本。现有 V1 保留原名和原始内容。

## 如何执行

每份 SQL 在所属服务的 `pom.xml` 中登记。system 的资源配置将当前 V1 从这个目录原样复制到运行包的 `db/system/1.0.0/`，Flyway 按已有 `classpath:db/system` 配置递归发现并执行。

以后新增 system 脚本时，在 `system-service/pom.xml` 的数据库资源 `includes` 中加入对应路径。其他服务的脚本由各自的资源配置选择，不能把整个目录的所有 SQL 无差别打进每个服务。

服务源码目录不再维护另一份 SQL。`target/` 和 JAR 中的 SQL 是自动生成的打包副本，请修改本目录中的原文件。

relations 当前没有业务数据库和迁移脚本，后续有实际表需求时再接入。当前建表仍由 system 启动时自动执行，也可以使用已有隔离数据库测试验证；不需要手动执行 V1。
