# 邮箱验证码注册、密码登录与手机号绑定

## 1. 先记住业务顺序

```text
填写昵称、邮箱 → 获取邮件验证码 → 提交昵称、邮箱、验证码、密码 → 注册成功
注册后 → 邮箱＋密码登录 → 返回 JWT
登录后 → 填写并绑定手机号 → 手机号＋同一个密码也能登录
```

注册和登录分开：注册成功只返回成功消息，不自动签发 Token。验证码仅用于注册，不能用于登录或重置已有账号密码。手机号暂时只验证格式和唯一性，不发送短信，不代表已验证手机号归属。

## 2. 第一步：写数据库增量脚本

脚本集中在项目根目录 `sql/`，在 `system-service/pom.xml` 登记后由 Flyway 执行。

| 脚本 | 作用 |
| --- | --- |
| `1.0.0/V1_1__user.sql` | 原用户表，邮箱和手机号分别唯一，保存 BCrypt 密码散列 |
| `1.0.1/V2_1__email_login.sql` | 已有的验证码存储及限额表迁移，保留历史，不修改内容 |
| `1.0.1/V2_2__email_registration.sql` | 将原标记重命名为 `email_verified`，表示邮箱已验证，并作废原登录用途的验证码 |
| `1.0.1/V2_3__user_nickname.sql` | 增加可重复的昵称字段，历史账号允许为空 |

用户注册时必须有昵称、邮箱、有效验证码和密码；手机号可以为空。昵称 `nickname` 去除首尾空白后必须为 1～100 个字符，允许重复；`username` 仍由后台自动生成，作为唯一账号标识。注册代码保存昵称、将密码加密保存，将 `email_verified` 设为 true，角色为空、管理员标记为 false。历史账号的昵称保持为空。

数据库暂时允许 NULL 密码以保留早前版本可能创建的测试账号；新注册接口禁止缺少密码，NULL 密码账号不能登录。本次不为历史无密码账号自动生成密码，也不允许通过重复注册覆盖；如果曾实际创建过这样的账号，需要通过已有管理员账号维护设置密码，再使用密码登录。

验证码存 `relations.sys_email_code`，仅保存带服务端密钥的 HMAC-SHA256 摘要；发送限额存 `relations.sys_email_send_limit`。邮箱按去除两端空白、转小写处理，注册不能重复占用已有邮箱，包括大小写变体及软删除账号。

## 3. 第二步：定义前端提交的数据

Java 文件在 `system-service/src/main/java/com/base/system/` 下：

| 文件 | 接收内容 |
| --- | --- |
| `modules/auth/dto/SendEmailCodeRequest.java` | 发码接收 email，并校验必填、邮箱格式和长度 |
| `modules/auth/dto/EmailRegisterRequest.java` | 注册接收 nickname、email、code、password，逐字段定义说明和校验规则 |
| `modules/auth/dto/LoginRequest.java` | 登录接收 account、password；account 可以是邮箱或手机号 |
| `modules/user/dto/UserRequests.java` 的 `BindPhone` | 绑定接收 phone，不接收要修改的用户 ID |

新设密码为 8～72 个字符，仅支持英文字母、数字和英文半角符号，不允许中文、全角符号、表情或空格；不要求三类字符同时出现。邮箱注册、管理员新增用户、修改密码及首位管理员初始化使用相同规则：长度不符提示“密码长度必须为8～72个字符”，字符范围不符提示“密码仅支持英文字母、数字和英文半角符号，不能包含空格”。这些字符在 UTF-8 中各占一个字节，字符数限制同时满足 BCrypt 的 72 字节上限，无需再向用户提示字节数。登录保留原有校验，历史中文密码仍可登录。验证码为六位数字字符串。手机号沿用现有国内手机号格式。原密码登录的 `email` 入参仍可使用，内部作为 `account` 处理。

认证请求 DTO 采用 PMS 风格的普通类：每个请求一个文件，使用 `@Data` 生成 getter/setter，使用 `@Schema` 描述字段，校验注解逐行展开。当前项目是 Spring Boot 3，使用 `jakarta.validation` 和新版接口文档注解，不直接复制 PMS 的公司内部注解。

`SendEmailCodeRequest`、`EmailRegisterRequest` 只定义字段、说明和校验注解，不编写处理逻辑。`EmailCodeServiceImpl.sendEmailCode()`、`register()` 先去掉邮箱两端空白并转小写，再通过 `Validator` 执行 DTO 上的校验规则，最后处理发送邮件或创建账号。这样 `"  Test@QQ.COM  "` 仍按 `"test@qq.com"` 处理。这两个 Controller 参数不使用提前执行的 `@Valid`；密码登录仍使用 `@Valid`。Controller、Service 使用 `request.getEmail()` 等普通 getter 读取参数。

`EmailCodeServiceImpl.register()` 同时使用 `strip()` 去除昵称首尾空白，再按 DTO 上的 `@NotBlank`、`@Size(max = 100)` 校验。昵称校验失败返回 400，不会消费验证码。

## 4. 第三步：配置并发送验证码

本机临时测试：在 `application-local.yml` 的 `app.email-code` 下设置 `test-mode: true`，重启并确保该本机文件已加载。可以跳过获取验证码，直接提交注册，`code` 固定填 `"123456"`，不需要配置 SMTP 和验证码密钥；其他验证码仍返回 401。昵称、邮箱、密码和重复注册校验继续执行。此开关默认关闭，恢复真实邮件验证码时改为 `false` 并重启。获取验证码接口仍走真实邮件发送流程。

1. 在发件邮箱服务商设置中开启 SMTP，取得授权码。
2. 参考 `system-service/src/main/resources/application-local.example.yml`，在被 Git 忽略的 `application-local.yml` 中补充邮件配置，保留原数据库及 RSA 密钥配置。
3. 填写 SMTP 主机、端口、用户名和授权码。默认 465 SSL；若使用 587 STARTTLS，则设置 `MAIL_PORT=587`、`MAIL_SSL_ENABLED=false`、`MAIL_STARTTLS_ENABLED=true`。
4. 配置 `app.email-code.from`（通常与发件邮箱一致）及独立的 `app.email-code.code-secret`（至少 32 字节）。如原本已填写 `app.email-login`，需把该配置节点改为 `app.email-code`。

可在本机生成独立随机密钥，再填入私有配置：

```powershell
[Convert]::ToBase64String([System.Security.Cryptography.RandomNumberGenerator]::GetBytes(32))
```

也支持环境变量 `MAIL_HOST`、`MAIL_PORT`、`MAIL_USERNAME`、`MAIL_PASSWORD`、`MAIL_FROM` 和 `EMAIL_CODE_SECRET`。授权码和密钥不要提交到仓库。未配置时应用仍可启动，发码接口返回 503。

`EmailCodeServiceImpl.sendEmailCode()` 的顺序：整理邮箱并校验参数 → 校验配置 → 锁定邮箱/IP 限额 → 判断频率 → 生成随机码 → SMTP 发信 → 保存摘要与过期时间。发送接口成功表示 SMTP 接受邮件，最终收件需检查收件箱及垃圾邮件目录。

```http
POST /auth/email/code
Content-Type: application/json

{"email":"your@example.com"}
```

规则：验证码有效 5 分钟、同邮箱间隔 60 秒、每邮箱每日尝试发送 10 次、每来源 IP 每日 50 次、每条码输错 5 次作废。日期按上海时区统计，SMTP 失败也计入限额；重发失败保留原来未过期的验证码。成功注册后验证码作废，每小时清理超过七天的过期记录。

IP 采用实际连接地址，不信任客户端自行传入的转发头。反向代理部署时会按代理地址统计，上线时需结合可信代理设置核对限流。

## 5. 第四步：校验验证码并创建账号

```http
POST /auth/email/register
Content-Type: application/json

{"nickname":"小明","email":"your@example.com","code":"012345","password":"your-password"}
```

`EmailCodeServiceImpl.register()` 的顺序：整理邮箱并校验参数（包含密码字符数和字符范围） → 检查密钥配置 → 锁定验证码行 → 判断过期/使用状态/错误次数 → 对比摘要 → 消费验证码 → 确认邮箱尚未注册 → BCrypt 加密密码并创建普通用户。

成功返回 `{"code":0,"message":"success","data":"注册成功"}`。错误次数独立提交，避免抛出业务异常后次数被回滚；成功消费与账号创建处于同一事务，并发使用同一条码只允许一个请求成功。旧账号返回 409，不会重设密码或绑定到新注册请求。

## 6. 第五步：邮箱或手机号＋密码登录

```http
POST /auth/login
Content-Type: application/json

{"account":"your@example.com","password":"your-password"}
```

绑定手机号后，同一接口也可以传：

```json
{"account":"13800138000","password":"your-password"}
```

`AuthServiceImpl.login()` 的顺序：按账号类型查询有效用户 → 校验 BCrypt 密码 → 查询当前权限 → 签发 RS256 JWT。邮箱优先精确匹配，没有精确匹配时仅在大小写归一化结果唯一的情况下登录，兼顾原来区分大小写的历史账号。

成功返回 `{"code":0,"message":"success","data":{"token":"JWT"}}`。后续请求携带 `Authorization: Bearer <token>`，可调用 `GET /auth/userInfo` 查看 `data.userInfo.nickname`、邮箱和已绑定手机号；历史账号的 `nickname` 可能为 null。

## 7. 第六步：登录后绑定手机号

```http
POST /user/bindPhone
Authorization: Bearer <token>
Content-Type: application/json

{"phone":"13800138000"}
```

`UserService.bindPhone()` 只使用认证主体中的当前用户 ID 更新手机号，不接受客户端指定其他用户。格式校验通过后更新，唯一约束阻止同一号码绑定到多个账号；重复占用返回 400。换绑后旧号码无法再用于该账号登录。该入口无需后台用户管理权限。

旧 `/user/register` 仅允许超级管理员调用，原 `/auth/email/login` 已移除，不能绕过密码登录。

## 8. 文件职责与验证

| 文件 | 职责 |
| --- | --- |
| `modules/auth/AuthController.java` | 发码、注册、密码登录和当前用户接口入口 |
| `modules/auth/EmailCodeService.java` | 声明验证码发送和注册方法，Controller 依赖此接口 |
| `modules/auth/impl/EmailCodeServiceImpl.java` | 实现参数处理、邮件、验证码、发送限制、注册和定时清理 |
| `modules/auth/entity/EmailCodeEntity.java` | 验证码普通实体类，承接数据库查询结果 |
| `modules/auth/entity/EmailSendLimitEntity.java` | 发送限额普通实体类，承接数据库查询结果 |
| `modules/auth/mapper/EmailCodeMapper.java` | 声明验证码与限额数据库操作，不内嵌 SQL |
| `system-service/src/main/resources/mapper/auth/EmailCodeMapper.xml` | SQL、字段映射和事务行锁 |
| `modules/auth/EmailCodeProperties.java` | 绑定发件地址与验证码摘要密钥 |
| `modules/auth/AuthService.java` | 登录与当前用户信息业务接口 |
| `modules/auth/impl/AuthServiceImpl.java` | 邮箱/手机号密码校验、JWT 签发及当前用户信息 |
| `modules/auth/AccessService.java` | 当前身份与授权业务接口，继承安全模块的 CurrentUserProvider |
| `modules/auth/impl/AccessServiceImpl.java` | 读取本地有效用户及其最新角色、操作权限 |
| `modules/auth/mapper/AccessMapper.java` | 角色、菜单和操作权限关联的数据库操作声明 |
| `system-service/src/main/resources/mapper/auth/AccessMapper.xml` | 角色、菜单和操作权限关联 SQL |
| `modules/auth/dto/LoginResponse.java` | 登录返回的 Token |
| `modules/auth/dto/UserInfoResponse.java` | 用户资料、权限和菜单的返回结构 |
| `modules/auth/dto/UserProfileResponse.java` | 用户基本资料，不包含密码散列 |
| `modules/user/UserController.java` | 提供当前用户手机号绑定入口及原用户管理入口 |
| `modules/user/UserService.java` | 当前用户手机号绑定、原账号维护；管理员改邮箱会清除邮箱已验证标记 |
| `modules/user/entity/UserEntity.java` | 映射用户字段、昵称和邮箱已验证标记 |
| `system-service/src/test/java/com/base/system/EmailRegistrationHttpTest.java` | 真实 HTTP、数据库、BCrypt 和 JWT，只替换外部 SMTP |

上述 `modules/` 路径相对于 `system-service/src/main/java/com/base/system/`。

注册链路按 PMS 的常用写法组织：`Request → Controller → Service 接口 → ServiceImpl → Mapper → XML`。请求类、查询实体、配置类采用普通类；实现类使用明确的变量类型和完整的依赖名称。Controller 调用业务方法后通过当前项目的 `ApiResponse.success(...)` 返回响应，接口路径和原响应字段保持一致。

auth 的 Service 已统一为下面的目录形式；根包里的 Service 只有接口声明，实际逻辑都在 impl 下：

```text
auth/
├── AuthController.java
├── AuthService.java
├── AccessService.java
├── EmailCodeService.java
├── EmailCodeProperties.java
├── impl/
│   ├── AuthServiceImpl.java
│   ├── AccessServiceImpl.java
│   └── EmailCodeServiceImpl.java
├── dto/       请求参数和返回结果，普通类逐字段定义
├── entity/    验证码与发送限额的数据库查询结果
└── mapper/    数据库操作接口，SQL 在 resources/mapper/auth/ 下
```

运行时 Controller 调用业务接口，由 Spring 注入对应的实现类；安全模块调用 CurrentUserProvider 时，实际执行 AccessServiceImpl。登录返回 LoginResponse，用户信息返回 UserInfoResponse，Controller 再统一包装。关联 Mapper 的方法以 find/get/insert/update/delete 表明操作类型。

事务仍使用 `TransactionTemplate`：验证码错误次数、邮件发送失败时的尝试次数需要先提交，再抛出业务异常。不能直接改成整段 `@Transactional` 后抛异常，否则这些次数会随事务回滚。

JDK 21 下从项目根目录执行 `mvn.cmd -s .mvn/settings.xml clean verify`。自动测试使用 H2，不发真实邮件、不操作实际 PostgreSQL。本次只修改 Java 后端，独立小程序需按「注册 → 密码登录 → 保存 Token → 绑定手机号」接入。

真实验收还需：配置 SMTP 并实际收件、启动服务执行 PostgreSQL 迁移、完成小程序联调。退出时清理前端 Token 和用户缓存；不会主动吊销已签发 JWT。密码找回、短信验证和自助修改邮箱不在本次范围。
