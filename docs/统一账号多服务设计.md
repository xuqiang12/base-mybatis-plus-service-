# 统一账号多服务设计

本方案已按用户确认的“四个模块、两个运行服务”实施；各服务共用账号和权限。

## 模块与依赖

- `base-common`：公共返回、异常、校验、日志、时间和文档依赖，不引入数据库或安全 starter。
- `base-security`：依赖 common，校验 RS256 Token、组装当前身份、检查方法权限并返回统一 401/403。通过 `CurrentUserProvider.currentUser(int userId, String token)` 获取当前身份，不依赖具体表。
- `system-service`：依赖 security，本地查询当前用户和实时授权；提供现有登录、用户、角色、菜单和权限接口，以及需要合法 Token 的 `GET /auth/access` 身份授权查询接口。只有该服务持有签名私钥。
- `relations-service`：依赖 security，通过携带原请求 Token 调用 system 的 `/auth/access` 获取实时身份授权；不加载用户管理组件、数据库或迁移。

公共类库通过显式 `@Import` 引入。无登录需求的服务只引用 common。需要认证的服务引用 security，默认保护全部非健康检查和文档接口；公开业务路径由该服务明确配置。

## 配置与数据

system 默认 8080，relations 默认 8081。双方使用相同 issuer 和 RSA 公钥，system 单独配置 PKCS#8 私钥。密钥从外部 PEM 文件读取，禁止内置生产密钥；测试使用专门的测试密钥。

数据库配置和 V1 的打包、执行归 system；SQL 源文件集中在根目录 `sql/`，按发布版本分目录，当前在 `1.0.0/` 下。保留原 `relations.sys_*`、Flyway 历史 schema、V1 文件名和内容，不重命名已有表，不操作实际数据库。各服务通过自己的 POM 登记并打包所属脚本。relations 将来有业务数据库时自行引入 MyBatis 和数据库依赖。

每次业务请求查询统一服务，不缓存授权，保持撤权和删除用户即时生效。查询的 Token 必须与 userId 匹配，统一服务不接受匿名用户 ID 授权查询。统一服务不可用时业务请求返回 503，拒绝继续执行；失效身份返回 401，权限不足返回 403。配置连接、读取超时，不自动重试。

## 范围

保留现有 API 路径、返回结构和管理规则。本次不引入网关、注册中心、Redis，不新增业务接口。菜单按应用归属和其他业务权限码属于后续实际功能开发，不在此次结构调整中增加表字段。

切换签名算法后旧 HS256 Token 失效，客户端需要重新登录。

## 验收

1. common 单独导入，无数据库、安全配置或 JWT 密钥也能启动并提供统一 HTTP 返回。
2. 两个可执行服务包独立启动；relations 中没有登录、管理路由和身份权限表。
3. system 保留现有管理接口测试，并使用 RSA 签发 Token。
4. 两个真实 HTTP 服务联合验证共享登录、401/403、授权后放行、撤权和删用户即时生效、统一服务不可用时拒绝访问。
5. 根目录 `mvn.cmd -s .mvn/settings.xml clean verify` 通过，文档与新运行方式一致。
