# 双账本业务隔离约定

确认日期：2026-10-31。来源：用户明确要求家庭记账、生意记账的表和接口完全独立，未来停用生意记账不牵涉家庭记账，并要求后续需求统一按此约定实施。

本文是两套业务边界的长期约定。既有家庭功能文档仍描述家庭业务；其中家庭归属、成员和资金规则不扩展为生意规则。具体已实现功能以模块说明、源码和测试为准。

当前已实施范围与接口见 [business-service 模块说明](../business-service/README.md)：客户、商品、销售、称重、计价及独立结算已提供；当前只做农户往来账。

## 1. 业务边界

| 内容 | 家庭记账 | 生意记账 |
| --- | --- | --- |
| 数据归属 | 既有家庭及家庭成员体系 | 一个账号一本总账，以登录账号为归属 |
| 档案 | 自己的亲友、分类、账户与业务档案 | 自己的农户客户、化肥商品、收付款账户及业务档案 |
| 业务表 | 既有家庭业务表 | `business` schema 下的 `biz_` 业务表 |
| 接口 | 既有家庭业务接口 | `/business/**` |
| 后端 | 既有家庭业务模块 | 独立 Maven 模块 `business-service`，包 `com.base.business` |
| 前端 | 家庭页面、API、业务转换和状态 | 生意页面、API、业务转换和状态独立组织 |
| 统计 | 只统计家庭业务 | 只统计生意的收付、欠款及未计价粮食重量 |
| 生命周期 | 按家庭业务规则处理 | 可独立停用、归档及移除 |

共用同一套账号登录、Token、Spring Boot 服务、PostgreSQL 数据源、通用返回、请求封装、校验和技术组件。业务隔离不要求另起数据库、部署服务或复制注册登录。

以下行为不属于默认允许的复用：

- 生意客户引用家庭亲友 ID，或生意商品复用家庭收支分类。
- 生意数据以 `family_id` 为归属，或通过家庭成员关系授予生意权限。
- 将生意记录写入家庭收支、借贷、账户、资金日志或其他家庭业务表。
- 家庭统计混入生意收付款、资金或欠款。
- 在一张公共业务表里加模式字段承载两套数据，或在一个业务接口里根据模式切换两套处理逻辑。
- 两套业务表互相建立外键，或业务 Service、Store 互相调用来同步数据。
- 修改、删除、退出或停用一侧业务时，连带修改另一侧业务。

同一个人可以在两套业务中各有独立档案。其名称、称谓、业务记录及删除状态不自动同步。将来如果确实需要跨账本联动，须作为新的明确需求设计，不提前实现自动同步或转账。

## 2. 一个账号一本生意总账

用户于 2026-10-31 进一步明确：一个账号就是一本生意总账，不需要创建、命名、选择账套，也不需要生意成员管理。

- 生意客户、商品、买卖、称重、收付款和抵账均以 `owner_id` 归属登录账号。
- 服务端从已验证 Token 获取账号 ID；新增、修改、列表、详情均按此归属处理。客户端不传 `bookId` 或归属账号 ID。
- 新账号直接查询空列表、直接新增客户，不要求初始化总账；没有创建/查询账套接口。
- 家庭成员关系不授予其他账号生意访问权；客户或单据 ID 也不能绕过账号隔离。
- 停用、归档一侧业务不改动另一侧数据；两套业务只共用登录身份及技术基础。
- 当前不实现多账套、共享成员、邀请加入等功能；后续必须有明确新需求才能增加。

## 3. 后端和数据库落点

继续使用当前单服务、MyBatis-Plus/JDBC、事务及 Flyway 能力，不增加微服务或额外数据源。

生意表集中放在 `business` schema，统一使用 `biz_` 前缀：

| 表 | 职责 |
| --- | --- |
| `biz_customer` | 农户客户档案 |
| `biz_product` | 化肥商品、袋重、品牌、规格和可空常用售价 |
| `biz_account` | 独立生意收付款账户 |
| `biz_grain_weighing` | 每车原始称重及计价原单关联 |
| `biz_trade` | 买卖单及客户、方向、日期、经营季 |
| `biz_trade_item` | 商品、数量、规格、成交价和原始金额快照 |
| `biz_settlement` | 收款、付款或抵账的结算单 |
| `biz_settlement_item` | 结算与具体买卖明细的关联及本次结算金额 |

当前不做进化肥、卖粮、库存、成本、费用和利润，不按早期规划继续增加相关表。历史迁移及客户类型列保留，API不再暴露或按客户类型筛选；新建固定写入farmer，修改不改写历史类型。

后端放在独立 Maven 模块 `business-service` 的 `com.base.business` 下，不依赖 `system-service` 或家庭业务类。启动模块通过运行时依赖和自动配置装配，按客户、商品、销售、称重计价、结算组织。接口使用 `/business/**`，例如 `/business/customer/create`、`/business/customer/list`、`/business/fertilizer-sale/create`、`/business/settlement/create`。前端 `/java-api` 是既有代理前缀，不改变后端业务命名空间。

后续变更以实际源码、迁移、接口和必要验证为依据，不把早期规划当作当前需求。

## 4. 已确认的客户与未结款规则

### 农户客户和快速录入

- 当前只管理买我们化肥、卖粮给我们的农户客户，不提供类型Tab、类型选择或商家身份分支；请求与响应不包含客户类型。
- 同一个客户可同时有买入和卖出业务，不按买卖方向重复建客户。单纯运输的司机不默认等同实际交易和结款方。
- 客户资料支持姓名、称谓；称谓选填。预先维护客户、商品、单位、规格和常用价格，日常尽量点选后只输入数量即可保存，实际成交价可修改。

### 列表显示剩余未结款

列表的“化肥”“粮食”金额表示各自剩余未结款，不是累计买卖金额。统一从我们这边计算：

```text
每笔未结金额 = 原始买卖金额 - 有效结算金额
某类商品余额 = 该类未结应收 - 该类未结应付
客户净余额 = 各类商品未结余额之和
```

正数表示对方欠我们，负数表示我们欠对方。历史原单按实际交易方向保留，不能因当前范围变化改写历史金额。

示例：张三拿化肥 1,000 元，还款 500 元；我们另收他小麦，应付 1,200 元：

```text
张三（大叔）              −¥700.00
化肥 ＋500｜粮食 −1,200
```

前端采用已确认的两行列表：姓名及称谓、右侧净余额；下方带正负号的化肥及粮食未结款。去掉余额正负说明栏和村庄、最近日期等额外行；新增“＋”悬浮在右下角。沿用既有米色导航、浅灰背景、白色列表、圆形头像、珊瑚红主色和蓝色负余额样式。

### 收付款和抵账可追溯

- 原始买卖金额保留；还款通过结算记录及其分配关系冲减具体欠款。
- 一次结算支持多笔原单，当前真实收付按所选剩余全额结清；历史部分结算及抵账分配继续保留，跨季仍能查清来源。
- 只分配用户所选原单，按日期及ID从早到晚分配并保存关系，不自动冲减其他未选欠款。
- 抵账须确认并记录两侧分别冲减的金额；抵账不产生实际现金收付。
- 张三示例确认抵账 500 元后，化肥为 0、粮食为 −700；实际付出剩余 700 元后，两类均为 0，方为全部结清。
- 净余额为 0 不能直接证明两类单据已结清。比如化肥 ＋600、粮食 −600 尚未确认抵账时，仍有双向未结款。
- 业务日期、所属经营季、实际结算日期及原始关联分别保存。上季结余由历史计算，不复制成下一季新欠款；历史时点余额按当时有效的结算计算。
- 金额使用整数分；重量、数量和单价使用精确小数，后端统一计算及舍入。保存、分配、抵账和余额校验在事务中完成，并处理重复提交及并发结算。

## 5. 当前往来账边界

卖化肥只记录应收；收粮先记录每车毛皮重，客户详情集中计价只生成应付。录单和计价不即时收付款。结清及抵账统一使用 `/business/settlement/create`，旧粮款部分付款接口已移除。

未计价粮食只保留重量，不能当作金额0的已结清账单。原单、商品快照、原始称重、实际收付款和抵账分配保留。进化肥、卖粮、库存、成本和利润不在当前范围，早期规划不作为后续开发要求。

## 6. 前端边界和独立停用

- 家庭和生意的页面、API、业务转换、Store 和统计分别维护。业务 Store 不互相导入或触发对方业务写入。
- 共用登录态、通用 HTTP 封装、视觉变量、纯展示组件、导航外壳和模式选择；模式选择只切换入口，不转换、复制或合并业务数据。
- 生意 API 层只声明请求并透传数据，转换与页面流程放在生意业务使用处。正式生意业务不能依赖草图示例数据或本机持久化模拟业务。
- 停用生意功能时可以关闭入口和接口，家庭业务仍须能启动并正常使用；不得要求先初始化生意数据或配置。
- 生意数据的导出、归档、删除及最终清理单独处理，不连带删除账号、家庭或家庭业务数据。
- 保留已执行的 Flyway 迁移和历史。生意迁移单独归档并按现有机制登记，不能通过删除、改写已执行迁移来下线功能。

## 7. 后续需求实施与验收

每项后续需求先明确属于哪套业务；生意需求默认只修改生意模块。涉及公共基础设施的调整应说明两侧影响，并验证家庭功能不因生意的启停而异常。

生意实施需验证按账号隔离、跨账号拒绝、收付款与抵账分配、重复提交、并发及跨季追溯。功能未完成时明确实际阶段，不把文档、占位页、示例草图或构建成功当成业务验收完成。
