# 生意记账已确认需求与 AI 开发交接

整理日期：2026-11-01（Asia/Shanghai）。范围：近期沟通的生意记账需求，尤其是新增的“文字解析自动填单＋人工确认”。本文不汇总既有家庭记账功能，也不表示下述功能已经实现。

本文可直接交给其他 AI 阅读，用于理解需求、检查现状和继续开发。整理本文不包含业务代码开发、数据库执行或部署。

## 2. 用户要做什么

已确认：维护独立的生意账，主要涉及化肥与粮食往来。客户、买卖、欠款、实际收付款、抵账均应可追溯，后续覆盖库存、成本与利润。

日常录入尽量简单：既可以选客户、商品、数量进行手动录入，也希望输入一句自然表达的消息，让系统自动填写账单，自己核对、修改后确认保存。

用户举例：

> 今天张三拿了十袋复合肥，一袋一百二，收了两百，剩下赊账。

用户进一步明确：实际说法可能不同，但意思类似，希望仍然可以识别填写。用户在了解费用后接受“文字解析自动填单＋人工确认”的路线，并要求说明如何实现。

当前接受的技术方向：不依赖付费语言模型接口，优先用业务规则、数字解析和账号内档案匹配实现。不能承诺规则解析可以理解任意自然语言；遇到无法确定的内容，应让用户补充或手动填写。

语音识别、图片识别属于前期咨询和探索，目前没有确认首版接入；不能自行采购云服务、部署模型或把这两项作为当前交付前提。

## 3. 已确认：家庭与生意业务完全隔离

- 两套业务独立维护数据表、接口、业务代码、数据归属、授权和统计。
- 不允许同一业务表加 `family/business` 类型区分两套业务，也不允许同一业务接口用模式参数切换两套业务。
- 生意表使用 `business` schema 和 `biz_` 前缀；接口使用 `/business/**`；后端代码放在独立 Maven 模块 `business-service`，包名 `com.base.business`。
- 生意不引用家庭亲友、分类、账户等业务档案，不调用家庭业务 Service，不建立两边业务表之间的外键。
- 不自动同步档案、账户、流水、余额和统计；不默认提供跨账本转账。
- 停用、删除、归档一侧业务，不能触发另一侧业务数据变更。
- 可以共用账号登录、Token、通用请求响应、校验、数据库连接、事务基础设施、技术工具和纯展示组件。
- 沿用单个 Spring Boot 启动服务与现有数据库、Flyway 基础设施，不为隔离业务默认新增微服务、独立部署或复制登录系统。
- 前端生意页面、API、业务转换、Store 和统计独立组织；模式切换只切入口，不复制或转换两边数据。
- 正式业务接真实接口，不能用设计图示例金额、本机模拟数据或失败后回退 Mock 冒充成功。

## 4. 已确认：一个登录账号一本生意总账

- 一个账号就是一本生意总账，不创建、选择、命名账套，不实现账套成员、邀请或共享授权。
- 生意数据使用 `owner_id` 归属当前账号；由服务端从已验证 Token 获取。
- 客户端不指定数据归属账号，不传 `bookId`，不能通过客户 ID、单据 ID 绕过归属校验。
- 同一家庭的成员不因此获得彼此生意数据权限；不依赖 `family_id` 或家庭成员关系。
- 新账号直接看到空列表并能新增客户，不需要先初始化账套。
- 文字解析时，客户和商品候选也只能来自当前账号，不能泄露其他账号的档案或历史价格。

## 5. 已确认：客户管理及列表

### 5.1 客户身份

- 统一管理农户客户、商家客户，涵盖化肥供应商与收粮商。
- 客户类型表示身份，不决定买卖方向。同一客户可能同时买我们的货，也卖货给我们，不按买入、卖出重复建档。
- 单纯运输的司机不默认成为实际交易或结款方。
- 姓名／名称必填，称谓选填；已有表单还包含选填电话、备注。客户类型直接点选，称谓自由输入。
- 支持新增、修改、查询、删除；客户余额不能直接编辑。

### 5.2 列表和操作

- 农户客户、商家客户两个 Tab。
- 两行列表：第一行头像、姓名及称谓、右侧客户净余额；第二行显示带正负号的化肥、粮食剩余未结款。
- 不额外加村庄、最近日期或余额正负解释栏。
- 右下角悬浮“＋”新增；列表左滑或长按提供修改、删除，详情也可修改。
- 沿用米色导航、浅灰背景、白色列表、圆形头像、珊瑚红主色、蓝色负余额样式。
- 删除必须先确认；任一应收或应付未结时不能删除。软删除保留客户实体及所有历史原单、结算和分配关系。
- 修改、新增成功后刷新；失败保留用户已填内容，不显示假成功。

## 6. 已确认：买卖、欠款、收付款与抵账

### 6.1 余额含义

以我们这边为视角：卖出形成应收，买入形成应付。正数表示对方欠我们，负数表示我们欠对方。

```text
每笔未结金额 = 原始买卖金额 - 有效结算金额
某类商品余额 = 该类剩余应收 - 该类剩余应付
客户净余额 = 各类商品余额之和
```

- 客户列表化肥款、粮食款是剩余未结款，不是累计成交额。
- 化肥不固定为正，粮食不固定为负；方向由实际交易决定。
- 总应收、总应付分别保留。净额为零，甚至同类净额为零，也不能据此判定原单全部结清。
- 应收、应付同时为零才算结清；有双向未结而净额为零时，保留“待抵账”事实。

### 6.2 原单、实际收付与分配

- 买卖原始金额、实际收付款、抵账、结算分配分别留痕，不能用改余额代替业务记录。
- 部分还款只冲减本次金额；原始成交金额不因还款而被覆盖。
- 一笔买卖支持多次结算，一次结算支持多笔买卖。
- 默认分配时，优先冲减对应方向较早的欠款并保存分配结果；用户指定原单时，保留指定关联。
- 即时收付款也应保存原单、收付记录和分配关系，在事务中保证一致。
- 收款、付款方向不能颠倒，不能超额核销；并发情况下重新校验有效未结金额。

### 6.3 抵账

- 抵账必须经过用户确认，不因客户净额为零自动发生。
- 保留两侧原单及各自冲减金额，抵账不产生现金收支。
- 一笔抵账的应收侧、应付侧核销金额应相同，且不超过各侧可结金额。
- 不得把两侧分配相加后，当成双倍抵账发生额。

## 7. 已确认：商品、快捷录入、单位、跨季与利润口径

- 预先维护客户、商品、单位、规格、常用价格，日常尽量点选后输入数量即可；实际成交价可修改。
- 后续覆盖化肥按吨进货、按袋销售，粮食按斤收购、按吨销售。
- 每袋重量和单位换算必须明确；保留成交时的原始数量、单位、单价和规格，不以当前档案覆盖旧单。
- 数量、重量、单价使用精确小数；金额使用整数分，由后端统一计算及舍入。
- 业务日期、原单所属经营季、实际结算日期分别记录。
- 跨季欠款仍关联旧原单，不复制成新季欠款；历史时点余额按当时有效的结算计算。
- 库存和成本跨季连续；已售商品对应成本结转为销售成本，未售商品保留库存成本。
- 收回欠款不重复确认销售收入或利润；抵账不产生现金流水。
- 运费等生意费用只影响生意统计。具体成本算法和费用是否分摊库存成本仍待定，见第 12 节。

## 8. 本次新增：文字解析自动填单＋人工确认

### 8.1 已确认的核心流程

```text
输入一段记账文字
  → 解析业务字段
  → 匹配当前账号的客户／商品
  → 自动填写可修改表单
  → 展示缺项、候选和冲突
  → 用户补充、修改并确认
  → 通过正式生意写接口入账
```

- 不要求用户严格按唯一模板说话，支持常用表达的词序、同义说法和中英文数字变化。
- 先做文字入口；用户可以自行使用手机输入法语音转文字，但不将其包装为项目已实现的录音识别功能。
- 不调用付费模型接口，不要求模型 API Key 或充值，规则解析在现有后端中运行；现有服务器的运行资源成本仍客观存在。
- 自动填单不等于自动入账。解析和预览阶段不能创建买卖、生成收付款或修改余额、库存。
- 无法确定时保留原文和待补字段，允许手动完成，不能猜测后直接保存。

### 8.2 需要提取的业务信息（需求细化）

| 信息 | 处理要求 |
| --- | --- |
| 客户 | 匹配当前账号已有客户；不存在、重名或不唯一时提示选择／补充 |
| 买卖方向 | 结合“卖给、从某人买、收购”等及其主语判断，不能按客户类型或商品类别固定方向 |
| 商品 | 尽量匹配已有商品与规格；“复合肥”对应多种商品时让用户选择 |
| 数量及单位 | 例如十袋、10袋、两吨、1000斤；数量与单价所用单位应一致或具备明确换算 |
| 单价与计价单位 | 例如每袋120、一袋120、120元/袋；不能把成交金额当单价 |
| 成交金额 | 可从文字提取，也可由数量和单价计算；两者不一致时提示冲突 |
| 本次实际收款／付款 | 区分收到、付给及动作主体；不把所有“付了”都当我们付款 |
| 本笔剩余未结金额 | 由确认后的成交金额和本次结算计算；不能直接当客户全部历史余额 |
| 日期 | 明确“今天、昨天、具体日期”时解析；相对日期按业务时区解释，确认表单展示实际日期 |
| 原文 | 填单过程中保留，便于用户核对；是否长期落库及保留周期待设计 |

经营季、资金账户等正式业务必填项，如文字未明确提供，应在表单展示默认候选或要求补选，不能由解析器编造。

### 8.3 常见表达与数字处理（需求细化）

以下三句在客户、商品均唯一的前提下，应形成相同的业务候选：

1. “今天张三拿了十袋复合肥，一袋一百二，收了两百，剩下赊账。”
2. “今天卖给张三复合肥10袋，120元一袋，收到200。”
3. “今天给张三送了十袋复合肥，总共1200元，他先付了200。”

其中“一百二”是口语写法，本例可提示候选 120 元供确认；不能把所有省略单位或位数的数字都无条件按同一种方式解释。“一块二”等小数、斤价与吨价也必须结合计价单位，不能直接做字符串替换。

应按数字周围的词、单位和动作关联字段，而不是按句子中数字出现的顺序依次填表。商品规格、名称里的数字不能直接当成数量、单价或金额。

完整示例的预览结果：

| 字段 | 候选值 |
| --- | --- |
| 客户 | 当前账号的张三 |
| 方向 | 我们卖出 |
| 商品／规格 | 复合肥；如不唯一，等待选定 |
| 数量 | 10 袋 |
| 单价 | 120 元／袋 |
| 成交金额 | 1,200 元，即 120000 分 |
| 本次收款 | 200 元，即 20000 分 |
| 本笔剩余应收 | 1,000 元，即 100000 分 |

确认后保存 1,200 元买卖原单、200 元收款及该收款对本单的分配。这里的 1,000 元只代表这笔交易剩余应收；张三最终总余额还要结合其历史记录计算。

### 8.4 不确定、缺失与冲突（需求细化）

| 输入／情况 | 预期行为 |
| --- | --- |
| “张三拿了十袋复合肥” | 填客户、商品、数量；单价可展示档案参考价供确认，收付款状态待补，不默认全收或未收 |
| “张三拿了1200元化肥” | 可提取客户、类别、金额，不编造具体商品、数量和单价 |
| “张三十袋，每袋120，共1500” | 显示 10×120=1200 与总额1500的冲突，要求修正／明确，不静默覆盖 |
| 当前账号有重名客户或多种复合肥 | 返回可选候选，不擅自选第一条 |
| 客户或商品不在当前账号档案中 | 提示选已有项或通过正常流程新增；解析时不悄悄建档 |
| “收了200”与“没收钱”同时出现 | 提示收付信息冲突，不取其中一个直接入账 |
| “欠1000，其他付了” | 核对是否明确指本笔；仅在含义清楚时给出推算候选，并展示推算依据 |
| “还是上次那个肥，老张十袋，价钱照旧” | 涉及别名、上下文及历史价格，不保证首版理解；无法确定就提示选择 |
| 一段文字含多客户、多商品、还款或抵账等混合操作 | 检测到未支持结构时提示拆分或手动录入，不丢掉后半句后显示全部识别成功 |
| 日期、斤／吨、袋重或付款主体有歧义 | 保留待确认项，不能猜测为确定值 |

无论解析是否完整，用户都应能修改候选表单。只有正式记账要求的字段齐全且冲突处理完毕，才允许确认保存。

### 8.5 解析与记账的接口边界（实现建议，不固定技术契约）

建议增加独立解析接口，例如 `POST /business/entry/parse`，提交原始文字，返回字段候选、档案候选、缺失项、冲突项及必要提示。这个路径曾在对话中作为示例提出，尚未实现，也不是不可更改的用户指定接口。

建议解析器在 `business-service` 内按文本规范化、数字／单位解析、档案匹配、业务规则校验拆分，避免一个超长正则承载全部逻辑。可以让响应区分原文提取值、计算值、档案默认候选和待确认值，便于前端展示。

最终保存复用正式买卖／结算能力。确认时服务端再次校验账号归属、客户状态、金额、分配和必要库存；不能因为之前解析通过，就信任客户端提交的金额及候选 ID。人工修改后的字段是本次提交依据，后端重新计算并校验一致性。

解析草稿是否需要持久化、如何记录输入来源和规则版本、返回字段名称及前端组件结构，由实现阶段设计；不能因此另建一套直接改余额的“文字账”。

## 10. 验收依据

以下是已确认业务规则对应的验收要求，以及文字填单目标的建议验收用例。具体用例实现由接手者完成，不代表当前已经通过。

### 10.1 生意基础闭环

假设张三初始无欠款：

| 步骤 | 操作 | 化肥未结 | 粮食未结 | 张三净余额 | 本次实际资金变动 |
| --- | --- | ---: | ---: | ---: | ---: |
| 1 | 卖化肥1000，未收 | +1000 | 0 | +1000 | 0 |
| 2 | 收款500，分配到化肥原单 | +500 | 0 | +500 | +500 |
| 3 | 收张三小麦1200，未付 | +500 | -1200 | -700 | 0 |
| 4 | 确认抵账500 | 0 | -700 | -700 | 0 |
| 5 | 实际付张三700 | 0 | 0 | 0 | -700 |

- 每一步保留原单和结算来源，不覆盖原始金额。
- 单独验证化肥+600、粮食-600时净额0但未结清；未确认抵账不能变成已结清。
- 跨季还款仍冲旧原单，不生成新欠款或重复收入。
- 数量、单位换算、金额舍入、部分结算、并发、重复请求和失败回滚正确。
- 跨账号访问拒绝，同家庭不共享生意；关闭生意功能后家庭仍可启动和使用。

### 10.2 文字填单

- 第 8.3 节的同义示例应得到一致业务候选，重名／多规格时应先消歧。
- 仅解析、修改草稿、取消确认均不能新增正式业务或影响余额。
- 缺项留空或标记待确认；参考价展示来源，不伪装成原话明确提供的成交价。
- 金额矛盾、方向不明、单位不明不能无提示保存。
- 手动修改后按修改后的表单入账，后端重算并校验。
- 完整示例确认保存后原单1200、收款200、分配200，本笔剩余应收1000；确认前不发生上述写入。
- 同一次保存重试不重复创建原单、收付和分配；失败不留下部分成功的账。
- 不支持的复杂输入明确提示，不截取一部分后误报完整成功。
- 候选查询和最终写入均验证当前账号，不泄露其他账号档案。
- 无模型 API Key、无付费模型服务时，规则解析及人工填写流程仍能工作。

## 11. 建议开发顺序（尚非用户指定排期）

1. 核对现有代码、迁移、测试、前端位置和未提交改动，建立真实完成清单。
2. 补商品／规格／单位及正式手动买卖录入；打通即时收付款、结算分配，按业务范围落实库存与资金影响。
3. 在同一正式表单上增加文字输入、规则解析、缺项／冲突提示和人工确认。
4. 补独立收付款、抵账及往来追溯，并明确这些操作何时纳入文字解析。
5. 按已经确认的业务方向逐步完善库存、成本、跨季、费用、利润；具体算法和启用衔接先解决待定事项。

可以调整顺序或先独立开发不落账的解析预览，但不能把演示预览、模拟保存当成已打通正式记账。未录入库存成本的历史买卖也不能默认为零成本后计算利润。

| 事项 | 已知边界 |

| 单独还款、抵账的文字理解 | 业务本身已有规则，但是否首版自然语言支持尚未确认；不能因为举过例子就宣称全面支持 |
| “发消息”的入口 | 已确认需要输入文字填单；是页面输入框、聊天样式，还是微信聊天消息接入，未最终指定；不默认接微信机器人、订阅号或企业微信 |
| 多轮对话 | “缺什么再补什么”可通过表单实现；长期聊天上下文和跨消息自动合并未确认 |
| 别名与历史价格 | 可作为匹配优化，客户别名字典、商品别名、自动取上次成交价的具体规则尚未确认 |

| 页面地图与交互细节 | 原设计稿供参考；首页、账单、我的布局及各入口不因本文自动成为本次全部交付项 |
| 资金账户 | 设计稿已提出生意账户及即时收付选账户；具体账户类型、期初、默认值和实现阶段需设计，不能复用家庭账户 |
| 成本算法 | FIFO、移动加权平均未选定，不能把设计示例当作算法决议 |
| 费用成本化 | 进货运费是否分摊库存成本待定，不能既资本化又重复扣经营费用 |
| 期初与启用衔接 | 库存、成本、历史欠款的初始化与正式启用日仍需设计 |
| 扩展业务 | 退货、损耗、盘盈盘亏、质量扣量、抹零、优惠、预收预付、跨客户抵账没有完整已确认规则 |
